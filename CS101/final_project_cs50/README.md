# TutorApp
#### Video Demo:  <URL (https://www.youtube.com/watch?v=vQhZohf2aYI)>
#### Description:

TutorApp is a small but complete Flask-based scheduling application designed for a tutoring workflow between professors and students. It allows professors to manage their student roster, create recurring lesson schedules, assign learning resources, and review payment submissions. Students can log in to see upcoming lessons, access professor-shared resources, and submit proof of payment for past sessions. The project is intentionally focused on a narrow domain: academic tutoring, scheduling, and administrative management. It is structured as a lightweight web app with a SQLite database, Flask routes, and Jinja templates that render a user-friendly interface.

At its core, the app is meant to help a tutoring business or individual instructor keep track of classes without needing a large-scale enterprise platform. The scheduling system is built around recurring classes, which is a practical feature because tutoring sessions often repeat weekly. The app also includes roster management, status tracking for classes, and a payment workflow in which a student submits a proof-of-payment reference and a professor confirms it. In that sense, this project is not only a UI prototype; it models the basic operational needs of an educational service: scheduling, communication, management, and payment verification.

The application’s main logic lives in `app.py`, which is the central file for all Flask routes and database interactions. That file defines the routes for login, registration, dashboard views, class scheduling, roster management, payment processing, and resource sharing. It also contains the route guards that restrict access based on role, ensuring that professors and students only see the parts of the app meant for them. The code includes validation for user input, protection for scheduled time conflicts, and simple checks to prevent invalid values from being written to the database. In addition to route handling, the application keeps session data for authenticated users and manages authentication through Flask session handling and hashed passwords using Werkzeug's password utilities.

The database schema is defined in `schema.sql`, and it is intentionally minimal but complete for the app’s scope. It defines three primary entities: users, schedules, and resources, along with the roster table that ties professors to students. The `users` table stores usernames, password hashes, and role information. The `schedules` table tracks each session with teacher and student IDs, a date, start time, end time, price, status, and optional payment proof. The `resources` table stores educational links assigned by a professor to a student, and the `rosters` table enforces the “many professors to many students” relationship with a unique constraint. The indexes on schedule and resource queries further show a design choice aimed at keeping lookups efficient as the app grows. This schema reflects a clear domain model: a professor teaches students, students attend sessions, and resources are shared within that relationship.

The `requirements.txt` file lists the dependencies needed to run the project, including `Flask`, `Flask-Session`, `cs50`, and a few supporting packages. This keeps the app easy to install and reproducible in a basic development environment. The project is intentionally lightweight and avoids heavy frameworks or unnecessary complexity, which suits its size and purpose. The use of SQLite as the database layer is another conscious design choice: it is simple to initialize, easy to store locally, and sufficient for a project focused on core functionality rather than large-scale production deployment.

The template layer is contained in the `templates` directory, and each file corresponds to a distinct page or flow in the app. `layout.html` is the shared base template and contains the navigation bar, flash message rendering, and common page shell. It also includes the shared Bootstrap and custom CSS assets. `login.html` and `register.html` provide the authentication screens, while `index_professor.html` and `index_student.html` render the professor and student dashboards. `classes.html` handles the recurring class creation form. `roster.html` manages the professor’s student list. `resources.html` provides the resource management screen for both roles, and `payments.html` is used for viewing past classes and handling payment status actions. The templates are intentionally straightforward, relying on Bootstrap for layout and structure while using a custom stylesheet to define the app’s visual identity.

The `static` directory contains assets used across the front end. `styles.css` defines the visual theme for the project, including the gradient background, card layout, form styling, and table presentation. This helps the app look cohesive and more polished without needing a large design system. A small `app.js` file handles a simple front-end interaction on the payments page, allowing the user to toggle between showing and hiding paid classes. This script is intentionally minimal and scoped to a single interaction so it does not bloat the front end or add unnecessary complexity. The project’s design choices emphasize clarity and maintainability over elaborate architecture, which fits a small course project or instructional demo.

One of the major design decisions in the project was to keep the logic in a single `app.py` file rather than splitting it into multiple modules. This makes the app easier to follow for a small project and reduces startup friction. The tradeoff is that the file can become large over time, but for this scope it is a practical choice that keeps the code easy to read and understand. The code also includes validation and role checks to preserve the integrity of the data model and avoid invalid actions such as scheduling outside a professor’s roster or submitting payment evidence without a real proof value.

Another design choice was to make recurring class creation explicit and transactional. Instead of scheduling one session at a time, the app generates a list of future class dates and validates conflicts across the entire series before inserting anything. This avoids half-created schedules and prevents accidental overlaps, which is especially important in tutoring because an instructor or student should not be double-booked. Similarly, the payment flow was built to require proof of payment before a class can move into a revision stage, preserving data integrity and making the workflow more realistic. These decisions reflect the app’s goal: to behave like a practical tutoring system rather than a purely decorative demonstration.

Overall, TutorApp is a compact, focused application that demonstrates core web-development concepts while solving a real scheduling problem. It combines Flask routes, SQLite persistence, templated UI views, role-based access control, validation, and a simple but realistic tutoring workflow. The project is intentionally easy to understand, but it still includes the kind of logic and structure that makes a web app feel functional and complete rather than toy-like. This balance between simplicity and practical usage is central to the project’s design, and it is one of the reasons the app is effective as both a course project and a useful prototype for a real tutoring service.
